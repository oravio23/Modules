# Lovable Handoff Runbook

**Status:** the code-level fixes below (§1) have been applied directly to this repo and verified —
`pnpm --filter @oravio/m5-documents test` (131 tests), `typecheck`, and `build` all pass clean as of
this revision, **and** §1c's fix was verified the way that matters: copying `apps/m5-documents` to a
directory outside the monorepo and running `npm install && npm run build` there directly, not just
reading the code. The infrastructure steps (§2–5) have not been run — they require an actual Supabase
Cloud project and a Lovable import to execute, which is for whoever runs the migration to do. See
[docs/lovable-import-prompt.md](lovable-import-prompt.md) for a paste-ready prompt covering §2–4 once
you're inside Lovable.

Everything marked **CONFIRMED** below was verified by reading this repo's files directly (cited inline).
Anything marked **must confirm during migration** depends on Lovable-internal or Supabase-Cloud-internal
behavior this audit could not observe from outside.

Per [ADR-012](adr/ADR-012-technology-stack.md), this stack (Vite + React + TS + Tailwind + shadcn/ui +
Supabase) was deliberately chosen to match what Lovable generates. That choice holds up — nothing here
requires a different framework or backend. What follows is what actually needs to happen, in order, plus
the specific things that will silently break if skipped.

**Docker is not part of this.** `supabase start` / Docker Desktop only exist for local dev. Lovable talks
to a hosted Supabase Cloud project over its own integration — the Docker container flakiness this repo
hit locally (see the two incidents earlier in this project's history) has no equivalent on hosted infra.

**What has never been tested:** per [CLAUDE.md §5](../CLAUDE.md), this app has only ever run against a
local Docker Supabase stack. It has never run against a real hosted Supabase Cloud project, never had its
Edge Functions deployed to Supabase's hosted runtime, and never been imported into Lovable. Nothing below
should be read as "this was already tried and works" — it's "this is what reading the code says will
happen," which is not the same thing until someone actually runs it.

## 0. Security — do this before anything else

**Rotate `ANTHROPIC_API_KEY`.** While auditing this handoff, a partial fragment of the real key ended up
in a few intermediate tool transcripts and temp files (now deleted). A key that's touched any log or
transcript should be treated as exposed regardless of how partial — rotate it at
console.anthropic.com → API Keys before proceeding, and set the new value only via `supabase secrets set`
(never in a file, never as a `VITE_` var).

**`supabase/.temp/` contained local secret files and was not gitignored — fixed.** Confirmed directly:
`supabase/.temp/start-secrets/supabase_edge_runtime_oravio-m5-document-ai/env` and sibling `secret-0`/
`secret-1`/`secret-2` files exist on disk, generated by `supabase start`, and no `.gitignore` line covered
`supabase/.temp/`. `.gitignore` now includes it — verified with `git check-ignore -v` against that exact
path. Still worth a manual double-check of `git status` right before your first commit, since this is
exactly the kind of thing worth not trusting blindly.

## 1. Code-level portability fixes — DONE, applied to this repo

### 1a. `xlsx` dependency pointed at a non-registry CDN tarball — HIGH, fixed
Was `package.json`: `"xlsx": "https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz"`. Verified directly: the
public npm registry only ever published `xlsx` up to `0.18.5` (with two unfixed CVEs); `0.20.3` only
existed via SheetJS's own CDN or the community republish `@e965/xlsx@0.20.3` (registry metadata confirmed
to match provenance). Whether Lovable's build sandbox would have allowed the arbitrary-CDN install was
never confirmed either way — the fix removes the ambiguity entirely instead: `package.json` now pins
`"xlsx": "npm:@e965/xlsx@0.20.3"`, resolved from `registry.npmjs.org` (confirmed in `package-lock.json`).
All three call sites (`src/lib/ingest/normalize/xlsx.ts`, `scripts/generate-fixtures.ts`,
`supabase/functions/_shared/xlsx-writer.test.ts`) import `xlsx` by name and needed no changes — a registry
alias, not an API change.

### 1b. `pdfjs` worker/font assets were staged only by `postinstall` — HIGH, fixed
`scripts/copy-pdfjs-assets.ts` copied pdf.js's worker + font/cmap files into `public/pdfjs/` via a
`postinstall` npm-lifecycle hook that ran `tsx` — a **devDependency**. Confirmed by reproducing the exact
failure locally: both `npm install --omit=dev` and `NODE_ENV=production npm install` failed with `'tsx'
is not recognized`. Separately, `public/pdfjs/` wasn't gitignored, so it was working by the accident of
`git add -A` picking the files up, not by design.

Fixed on both fronts:
- The script is now [scripts/copy-pdfjs-assets.mjs](../scripts/copy-pdfjs-assets.mjs) — plain `.mjs` using
  only `node:fs`/`node:path`/`node:url`, no dependency needed to run it at all.
- `build` now runs it explicitly (`"build": "node scripts/copy-pdfjs-assets.mjs && tsc -b && vite
  build"`), not just `postinstall` — confirmed by deleting `public/pdfjs/` and running `npm run build`
  alone (no reinstall): the old setup silently produced a `dist/` with no `pdfjs/` folder at all; the
  fixed setup regenerates it every time, verified by checking `dist/pdfjs/` contains
  `pdf.worker.min.mjs` + `standard_fonts/` + `cmaps/` after the same test.
- `public/pdfjs/` and `supabase/.temp/` are now both in `.gitignore` (correctness no longer depends on
  what happens to be present when someone runs `git add -A`).

Two things depend on these assets at runtime, unchanged: [src/lib/pdf/pdfjs-setup.ts](../src/lib/pdf/pdfjs-setup.ts)
(worker/font URLs) and [src/lib/ingest/normalize/pdf.ts](../src/lib/ingest/normalize/pdf.ts) (an
**uncaught** `await getPdfDocument(...)` — if the worker URL 404s, the whole PDF upload rejects, surfacing
as "Couldn't render page" in [PartViewer.tsx](../src/components/review/PartViewer.tsx)). After deploying
on Lovable, sanity check: `curl -I https://<your-domain>/pdfjs/pdf.worker.min.mjs` should return a JS
content-type, not `text/html` (an HTML response means the asset 404'd and got SPA-fallback-routed).

### 1c. Cross-boundary imports — this conclusion was wrong, now fixed
This section originally checked one `import type` (from `uploadDocument.ts`) inside the pre-monorepo
standalone repo, found it erased at build time, and concluded "no action needed." That check was
incomplete in two ways once this app moved into the monorepo, both confirmed by actually copying
`apps/m5-documents` out to its own directory and running `npm install && npm run build` there (not just
reading the code, which is what missed this the first time):

1. **Two imports are runtime, not type-only** — `src/lib/arabic.ts` (`export *`) and
   `src/lib/profiles/registry.ts` (`import { ALL_PROFILES }`) — and both resolved only because the
   monorepo root happened to sit a fixed number of directories above this app. Copy the app out and
   Rollup fails immediately: there is no `supabase/` at that relative path any more.
2. **Three more are `import type`, but `tsc -b` still fails on them anyway.** Type-only imports are
   erased by esbuild/Vite at bundle time, but `tsc -b` — which this app's own `build` script runs
   *before* `vite build` — still resolves every import to check it, type-only or not. `src/lib/ingest/types.ts`,
   `src/lib/profiles/types.ts`, and `src/lib/upload/uploadDocument.ts` all reach across the same way and
   all failed `tsc -b` once copied out, even though `vite build` alone would have been fine with them.

**Fixed:** all five now import from `src/lib/_shared-vendor/`, a real (not re-exported) copy of the
subset of `supabase/functions/_shared/` this app needs at build time, produced by
[`scripts/vendor-shared.mjs`](../scripts/vendor-shared.mjs). That script runs on `postinstall` and is
prefixed onto `build`, and degrades to a no-op with a log line if `supabase/functions/_shared` doesn't
exist (i.e. running outside the monorepo) — the vendored copy is committed to git, not gitignored,
specifically so the build doesn't depend on the monorepo being present to succeed. Re-run it after
editing anything in `supabase/functions/_shared/{arabic.ts,envelope-types.ts,parts.ts,profiles/*,pipeline/stages.ts,contracts/register.ts}`
from inside the monorepo, the same way `scripts/sync-ui.mjs` works for `packages/ui`/`packages/tokens`.

Create a new project at supabase.com, then from this repo:


### 2b–2d. Superseded — this whole section described the pre-monorepo pilot
Everything that used to live here (push `0001_init.sql`/`0003_seed_profiles.sql`, enable anonymous
sign-ins because there's no login flow, confirm the Storage bucket and Realtime publication) described
the standalone M5 pilot from before this app moved into the monorepo. None of it is accurate any more:

- Migrations are now `0001_platform_core.sql` through `0008_org_auto_provisioning.sql` (nine files, not

## 3. Deploy the Edge Functions

```bash
supabase functions deploy documents-register
supabase functions deploy pipeline-worker --no-verify-jwt
supabase functions deploy export-result
```

`pipeline-worker` needs `--no-verify-jwt` — `config.toml`'s `verify_jwt = false` for it is local-only
and does not carry to a cloud deploy. Without the flag, `documents-register`'s fire-and-forget call to
it (a service-role bearer token, never a user session) gets rejected with a 401 before the pipeline ever
starts. `documents-register` and `export-result` keep the default JWT verification.

### 3a. Hosted execution-time limits — already designed for, not a fresh risk
This was the biggest concern going in (a ~40s local pipeline run against hosted Edge Function wall-clock
limits), but reading [pipeline-worker/index.ts](../supabase/functions/pipeline-worker/index.ts) directly
shows it was already built with this in mind:
- `TIME_BUDGET_MS = 100_000`, with an explicit comment: *"Safety margin under the free-tier 150s edge
  function wall-clock limit."*
- The `transcribe` stage checks elapsed time after each batch and **self-reinvokes** via `reinvokeSelf()`
  (a `fetch` back to its own URL with the service-role key) if there's more work and the budget's used up,
  rather than trying to push through in one call.
- `documents-register` triggers `pipeline-worker` fire-and-forget on purpose (commented as intentional) —
  the browser gets an immediate response and watches progress via Realtime instead of blocking on the
  whole pipeline.

Residual note, not a blocker: only the `transcribe` stage has this self-reinvoke safety net. `classify` and
`extract` are each a single Anthropic call and run to completion in one shot with no chunking — for an
unusually large/complex document (long `commercial_invoice` extraction at `xhigh` effort, or a very long
transcript), a single `extract` call could in principle still approach the 150s ceiling with no fallback.
Worth watching for during the first real smoke tests with larger documents, not something to pre-emptively
rewrite.

**Must confirm during migration:** the exact current wall-clock/CPU limits for your plan tier (this code
assumes a 150s free-tier ceiling; paid tiers may differ) — check Supabase's current docs rather than trust
a number baked into a code comment.

### 3b. `verify_jwt = false` on `pipeline-worker` — must confirm during migration
[supabase/config.toml:44-48](../supabase/config.toml) sets `verify_jwt = false` for `pipeline-worker`,
with a comment explaining it's only ever called with the service-role key as bearer token, never from the
browser. Whether a cloud deploy honors this per-function `config.toml` setting automatically, or requires
an explicit `--no-verify-jwt` deploy flag, depends on your Supabase CLI version — confirm this at deploy
time. In practice this is likely a non-issue either way, since a service-role key **is** itself a validly
signed Supabase JWT — Supabase's JWT verification checks signature validity, not "is this an end-user
session" — but confirm rather than assume if the self-invocation starts returning 401s.

### 3c. CORS — already handled
Both `documents-register` and `pipeline-worker` set explicit CORS headers and handle `OPTIONS` preflight
requests directly in code. No action needed.

## 4. Configure secrets and frontend env vars

### 4a. Server-side secret (Edge Functions only)
```bash
supabase secrets set ANTHROPIC_API_KEY=<your-rotated-key>
```
Confirmed nowhere in `src/` does anything read `ANTHROPIC_API_KEY` (grepped the whole frontend tree) — it
never reaches the browser bundle. `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are auto-injected into
Edge Functions by Supabase Cloud; nothing to set manually for those.

### 4b. Frontend env vars (set in Lovable's environment config)
From [.env.example](../.env.example) and every `import.meta.env` reference in `src/`, exactly two vars are
required:
- `VITE_SUPABASE_URL` — your cloud project's API URL (Dashboard → Project Settings → API).
- `VITE_SUPABASE_ANON_KEY` — the anon/public key from the same page.

[src/integrations/supabase/client.ts:6-12](../src/integrations/supabase/client.ts) throws at module load
if either is missing — this fails loudly (a visible thrown error, not a silent blank page), but confirm
both are set in Lovable's project settings *before* the first build, not after.

**Naming to watch for:** newer Supabase dashboards show "publishable" / "secret" key naming alongside the
legacy anon/service_role JWT naming. This code expects the anon/public **key value** regardless of which
label the dashboard shows it under — copy the value, not necessarily the exact field labeled "anon key" if
your dashboard has been migrated to the new naming.

## 5. Import into Lovable and smoke-test

1. `git init` has already been run in this repo (as part of verifying the `.gitignore` fixes actually
   match). Nothing has been committed yet. Run `git add -A && git status` first and confirm
   `supabase/.temp/`, `public/pdfjs/`, and any real `.env.local` do **not** appear in the staged list
   before committing — then `git commit`, push to GitHub, and import into Lovable.
2. Set the two frontend env vars (§4b) in Lovable's project settings.
3. **Must confirm during migration** (genuinely Lovable-internal, not verifiable from this repo): whether
   Lovable's Supabase integration can deploy Edge Functions itself, or whether that must be done via the
   Supabase CLI as in §3 regardless of using Lovable for hosting. Don't assume either way going in.
4. First build — watch for the `xlsx`/`postinstall` issues in §1 if they weren't fixed first.
5. End-to-end smoke test: upload a small synthetic fixture from `fixtures/` → watch it move through
   transcribe → classify → extract → anchor → validate in the Queue page (Realtime progress) → open Review
   → confirm evidence anchors and validator results render → Finish review → Export.
6. If a job fails, check `jobs.last_error` (surfaced in the UI as "Pipeline failed") — there is currently
   **no retry button** for a failed document; re-uploading the same file is the only path back in if
   something goes wrong on this first real run.

## 6. Honest scope of what this covers

This audit could not fully complete two of its five planned dimensions (secrets/config handling and
broader operational/runtime gaps) through automated subagents — both were independently found to have
pulled real credential fragments into their own working transcripts, which is a safety violation
regardless of the finding's accuracy, so that automated output was discarded rather than used. Sections 0,
2c, 3a–3b, and 4 above cover the load-bearing parts of what those two dimensions were meant to check,
re-verified directly against the source by hand instead. What's **not** re-covered by hand and should get
extra attention during the actual migration: exact file-size ceilings on the Storage/Anthropic-Files-API
upload path (no explicit client-side size guard was found in `src/lib/upload/`, so limits are whatever
Storage/the Files API enforce natively), and realistic per-document Anthropic cost at scale (every
pipeline stage uses `claude-opus-5` — see
[supabase/functions/_shared/anthropic.ts](../supabase/functions/_shared/anthropic.ts) — with no rate limit
or concurrency cap in this codebase).

Per [CLAUDE.md §5](../CLAUDE.md), none of the following have happened yet, and this migration doesn't
change that on its own: no live end-to-end run against real infrastructure, no `npm run eval` run against
a real API key, no benchmark, and the Field Catalogue / Result-Envelope / Validator Catalogue are all
PROPOSED substitutes for specs that were never supplied. Getting this hosted on Lovable does not itself
validate any of those — it just removes Docker/local-stack fragility as a variable.
